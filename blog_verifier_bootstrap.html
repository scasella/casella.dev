A small model can mine its own bug-fixes from a test suite

No labels and no teacher model: a frozen Qwen2.5 proposes patches, a pytest verifier keeps the ones that pass, and reinforcement learning turns them into weights. Two facts shape it. Under its plain prompt the model mines zero fixes; rewrite the prompt and the same frozen weights start producing them. And model size, not the size of the mined pool, caps what the model learns. Measured 1.5B–7B, on synthetic and real HumanEvalFix bugs, for about $10.

TL;DR

If you ship software you already own a label-free reward signal for a code model: the test suite. A model proposes a patch, pytest says pass or fail, and a passing patch is a correct fix the model wrote itself, training data with no annotator and no larger model in the loop. A small open model can bootstrap on this. The catch shows up at the first step. Under its normal deployment prompt a 1.5B model mines zero verified fixes, at 1.5B and 3B, on synthetic and real bugs. The capability sits in the weights; the plain prompt does not draw it out. Rewrite the prompt against the verifier and the same frozen weights start producing real fixes (0 → 16 of 80 real bugs at 1.5B; 4 → 39 at 7B).

Model size then caps what the model keeps from that data. Reinforcement learning against the verifier converts the mined fixes into weights; more fine-tuning does not (+0.105 ± 0.022 over supervised fine-tuning across three seeds; doubling the data moved nothing). Held-out repair on disjoint real bugs ceilings at 1/40 → 5/40 → 6/40 from 1.5B to 7B, and a 7B mining its own doubled pool adds one task. The loop costs about $10 and needs no labels. Below ~7B the model learns your specific test distribution, and that knowledge does not carry to unfamiliar code.

Why this matters

Most claims of a "self-improving model" are promises. The small, honest version is a closed loop you can run: the model generates candidate solutions, a verifier keeps the correct ones, and the model trains on its own verified output. For code the verifier is free and already in your repo. It is your test suite. No human grades anything, and no bigger model tutors it. If the loop works, a budget model improves on your code for the price of the compute.

The obvious worry is circularity. A model that grades its own homework against tests it can see will learn to satisfy those tests instead of fixing the bug, and "self-training" turns into training on garbage. Three questions decide whether it is real: what gates the loop, whether the model can game its grader, and how far the learned skill reaches past the bugs it practiced on. I ran the loop end to end on a small setup, then spent the rest of a ~$10 budget mapping where it works and where it stops.

Terms used below
  • Mining. Sampling candidate patches from the model and keeping the ones the verifier accepts. The kept patches are self-generated, label-free training data.
  • The verifier · public vs hidden tests. Each task ships a small set of public tests (shown to the model, used as prompt feedback) and a separate set of hidden tests (never shown). A patch is a verified positive only if it passes both. The hidden tests are the external arbiter; they keep self-training from being circular.
  • Prompt optimization. An evolutionary search over the system prompt, scored against the verifier, plus optional localized pytest-trace feedback. It changes the wording, never the weights.
  • SFT vs GRPO. SFT (supervised fine-tuning) trains the model to imitate the kept fixes. GRPO is the reinforcement-learning step: the model samples groups of attempts, the verifier scores them, and the update moves the policy toward the higher-reward ones. Both turn mined data into weights.
  • Held-out · X / N. Every number here is on tasks the model never trained on. 23/38 is 23 of 38 held-out tasks repaired; 6/40, 6 of 40 held-out real bugs. A task counts only if the patch passes the hidden tests: binary, no partial credit.
  • Cold start. The sparse-reward regime where the policy never hits reward, so there is no advantage signal and RL has no gradient to follow.
  • HumanEvalFix. A public benchmark of real single-function Python bugs, each with a test suite. I rebuilt 160 of its tasks into the harness, pytest-checked so the buggy code fails and the gold fix passes both splits.

The loop

The mechanism is mundane on purpose: you could wire it to a CI suite you already run. A task is one buggy Python function plus its tests. The model emits a small {"old": …, "new": …} search/replace patch. A sandbox applies it and runs pytest. The public tests feed back into the next attempt; the hidden tests decide a binary reward. A patch that earns reward 1 is a correct fix the model wrote itself.

That gives two ways to improve the model from its own output: distill the verified fixes into the deployment prompt (no training), or fine-tune or RL on them (weights). Two questions follow: which step is the bottleneck, and which update banks the gain. The base model is Qwen2.5 at 1.5B, 3B, and 7B. Everything runs on one commodity GPU, an L4, with an L40S for the 7B, and I gate every paid run with a printed cost preflight.

Under the plain prompt, the model mines nothing

The most reproducible result in the project is a zero. Under the static deployment prompt the model mines no verified positives at 1.5B or 3B, on synthetic templates and on real HumanEvalFix bugs. Under that same prompt the base model repairs 0/40 held-out real bugs at 1.5B, 3B, and 7B. The capability sits in the weights; the prompt does not draw it out.

Optimize the prompt against the verifier and the same frozen weights start producing verified fixes. The jump is large.

This also explains a failure that looks like an RL problem but comes from the prompt. Sparse-reward reinforcement learning needs the policy to hit reward sometimes, or there is no gradient. Under the static prompt it never does: I measured 0% of sampled groups with both a pass and a fail, so the advantage is zero everywhere and GRPO cannot start. The optimized prompt creates reward variance on 25% of tasks. Prompt optimization is the exploration bootstrap that makes verifier-RL viable.

RL banked the gain; fine-tuning on more data did not

With the data mined, how do you put it in the weights? I ran every update off the same verified-positive pool and varied only the training step. Supervised fine-tuning on more self-mined data scored lower than fine-tuning on less. The reinforcement-learning step beat both.

Update from the same mined poolHeld-out repair (of 38)Rate
base · static prompt, no training0 / 380.000
SFT · on the 2×-larger mined pool21 / 380.553
SFT · on the smaller pool23 / 380.605
GRPO · against the verifier (3-seed mean)27 / 380.711

Reinforcement learning beat fine-tuning by +0.105 ± 0.022 in held-out repair rate, and it held across all three seeds (per-seed 28, 26, 27 of 38), the error bar clear of zero, with training reward climbing to 0.95–0.99 each run. Supervised fine-tuning went the other way: doubling the self-mined pool lowered held-out repair (0.605 → 0.553), the usual sign of fine-tuning narrowing onto the larger sample. The cold-start control, GRPO from the base model under the static prompt, stalled at 0/38 on every seed. Without the warm start from mined data there is no gradient. Only RL turned the better mining into better weights.

One in five passing patches failed the hidden tests

Self-generated training data is safe only if the model cannot game the judge, so I audited it. Of the patches that passed the visible tests, ~21% failed the hidden ones (20.9% under the scalar prompt, 21.3% under the localized one; the optimized prompts did not hack the verifier harder than the baseline). The hidden-test gate caught all 42 of those reward-hacks before they reached training. The leak sat in one place: 100% of it came from a single weak-verifier category whose public test under-specified the fix, and every other category leaked 0%.

One example shows why the held-out gate is load-bearing. On a sum-a-list bug the model left the wrong initializer in place and rewrote the body to total = sum(values). That returns the right answer on the visible example [2,3,4] and the wrong one on the hidden empty case []. The model satisfied the test it could see without fixing the bug. A visible-only reward would have admitted a fifth of the pool as garbage. The held-out gate removed all of it.

Bigger models clear the wall, then plateau

On real bugs, model size decides how much the loop pays off downstream. A 1.5B trained on its own real-bug fixes repairs 1/40 held-out real bugs. Hold the training data fixed and swap only the model: repair rises with scale, then flattens.

I asked the cheap question before the expensive one. The ~7/40 ceiling could be data-limited (too few mined examples) or capacity-limited (the model cannot generalize repair to disjoint real programs). A stronger miner lifts the data side: the 7B mines a 43-task pool, double the 1.5B's 21. Fine-tuning on that doubled pool moved held-out repair from 6 to 7 of 40. Past ~7/40 the bottleneck is capacity, and more self-mined data does not move it. The full per-condition picture, with cost:

Each rung cost under a dollar: the whole project, across mining, training, and evaluation at every size, came to about $10. The scale-up did add one wrinkle. At 7B the static prompt mines a faint 4/80 instead of zero, so "static = 0" is a small-model effect that fades as the base model strengthens. The prompt is still a ~10× lever there (39 vs 4).

The reusable parts

Two artifacts outlast the project. First, the harness: a verifier-bootstrap pipeline with a JSON search/replace patch contract, a sandboxed public/hidden pytest verifier, and a mine → SFT → GRPO loop that runs on one commodity GPU and prints a cost preflight before every paid run. Second, a pytest-verified real-bug dataset: 160 HumanEvalFix tasks rebuilt into the harness's shape. I check each at build time so the buggy code fails and the gold fix passes both splits, which gives a clean substrate for testing self-improvement on real code without a benchmark dependency at run time.

Bounds

This is single-function Python repair on one real benchmark (HumanEvalFix, 160 tasks, a 120/40 split), with pools of ≤43 verified positives. I ran the real-bug and scale results single-seed, on n=40 held-out eval. The 1.5B → 3B jump is large; the 3B-vs-7B difference sits inside the noise. Models span 1.5B–7B only.

The RL-beats-SFT result is the one replicated finding (three seeds, error bar clear of zero), but it is on the synthetic suite. The GRPO step is a small on-L4 pilot, and I did not re-run it on real bugs. The cheap data-bottleneck test (doubling the pool bought +1/40) predicted the same capacity wall: RL optimizes the policy on the training tasks and adds no generalization capacity. I recorded the prediction and declined the spend instead of reporting a result I did not run.

The flattering synthetic number does not transfer. Held-out repair looked strong on templated bugs (0.605), but that leaned on template structure shared between train and test. On disjoint real programs it collapses to 1/40 at 1.5B. Novel-category generalization stays out of reach: pulling held-out categories into the RL pool did not move them. The loop mines and banks verified fixes; below ~7B it does not generalize repair, and the two claims come apart.

Close

The recipe is short. A test suite is a free reward signal, and a small open model can mine verified-correct fixes against it and learn from them. Three steps make it work: optimize the prompt first, hold out part of the verifier as a gate the model cannot see, and bank the gain with reinforcement learning instead of fine-tuning. The same runs set the boundary. Whether the self-mined data generalizes to unfamiliar real code depends on model scale, and below ~7B the model learns your specific test distribution. That knowledge does not carry to new code.

Two things would turn this from a measurement into a tool, and I ran neither: a full 7B reinforcement-learning pass on real bugs, and a base model strong enough that the prompt stops being the gate. Until then the bounded claim holds, and it is a useful one. The method is cheap and needs no labels, and I mapped how far it reaches before it stops.
